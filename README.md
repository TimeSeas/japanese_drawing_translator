# 日文零件图纸术语自动翻译系统

打开一张日文机械零件图纸（图片或 PDF），自动框出上面的日文注记，查术语词典翻成
中文，用红字标回原图对应位置，结果可以导出成 JSON。

做的是一件很具体的事：对日加工的图纸基本只有日文，看不懂日文的工艺、检验人员需要
一份能对着图看的中文标注。整条链路都在本机跑，图纸不外传。

## 功能

- **输入** —— PNG / JPG / BMP / PDF。PDF 按 300 DPI 逐页渲染，界面里可翻页，
  每页单独识别；图像型 PDF 走 pdf2image，取不到内容再退回 pypdf 抽内嵌图
- **识别** —— PaddleOCR PP-OCRv4 日文模型。低于置信度阈值的直接丢掉，重叠的框按
  IoU 合并，同一行被切碎的相邻框再按 x 接回整句
- **翻译** —— 963 条日→中机械术语词典。精确匹配优先，没命中就用编辑距离做模糊
  匹配，阈值可在 `config.yaml` 调。没有假名的行（`技術部`、`正面図`、`SUS304`、
  `縮尺1:2`）默认不翻 —— 中文读者自己看得懂，盖红字只是添乱
- **标注** —— 红字画回原图，**保留日文原文**：译文挪到旁边，并做碰撞检测避免译文
  互相压住。不提供"盖住原文"模式 —— 这是个核对工具，把要核对的东西盖掉就本末倒置了
- **导出** —— 标注图（PNG / JPEG / PDF）、结果 JSON（含原文、译文、坐标、两个
  置信度、匹配方式）
- **词典可编辑** —— 界面里增删改查，改完直接落盘
- **不卡界面** —— 识别和翻译跑在 `QThread` 里，处理大图时窗口照常响应，进度条实时更新

## 快速开始

需要 Windows + Python 3.8 以上。

```bash
git clone https://github.com/TimeSeas/japanese_drawing_translator.git
cd japanese_drawing_translator
pip install -r requirements.txt
python main.py
```

首次运行 PaddleOCR 会下载日文模型，之后就可以离线用。

## 使用

1. `文件 → 打开文件`（或工具栏 `打开文件`）选一张图纸
2. 点 `▶ 执行识别与翻译`
3. 图纸上出现红字译文；下方表格逐条列出原文、译文、匹配方式、置信度和坐标
4. `文件 → 导出标注图纸` 或 `导出翻译数据 JSON`

PDF 多页时左下角有 `上一页 / 下一页`。表格的「匹配方式」列把结果分成四类：`精确`
（词典里查到的）、`模糊`（机器猜的，复核时重点看）、`无需翻译`（中文读者自己看得懂）、
`-`（该翻但词典里没这个词，要往词典里补）。筛选下拉框按这四类过滤；点图纸上的标注框
会跳到表格对应行，点表格行也会在图上高亮。

`examples/` 下有一组完整样例：`demo-input.png` 是输入，`demo-output.png` 是标注结果，
`demo-output.json` 是导出的数据。另外两张 `test-*.png` 是构造出来的对照实验图 ——
`test-rule.png` 验竖线否决（同文字同间隙，只差中间有没有一条表格线），
`test-orientation.png` 验方向检测（竖排 + 斜排 + 一个离得很近的横排）。

## 数据流

```
文件 → file_parser.parse_file()       → [PIL.Image, ...]          每页一张
     → image_processor.preprocess()   → PIL.Image                 灰度/降噪/二值化
     → ocr_engine.recognize()         → [{id, text, bbox, confidence,
                                            orientation, parts}, ...] 已同行接龙
     → main_window._translate_item()  → 查词典；整句查不到时拆回碎片重试
     → overlay_renderer.render()      → 标注好的图
     → data_store.save_result()       → output/*.json
```

`config.yaml` 里 `ocr` / `translator` / `overlay` / `logging` 四段是原样传给对应
模块构造函数的（键名就是参数名），`preprocessing` 那段逐页传给 `preprocess()`。
所以加减参数只要同时改配置和构造函数，中间没有第二份默认值。

## 几个实现上的取舍

**模糊匹配用 `partial_ratio`，但要卡一下词条长度。** OCR 有时会把相邻的两行标注并进
同一个框里，`ratio` 会因为多出来的字符把分数拉低，所以用 `partial_ratio`。

但 `partial_ratio` 有个坑：**只要短串是长串的子串，它就给 100 分**。于是词典里那些
两三个字的通用词条变成了吸铁石 —— 一整行注記只要碰巧含「公差」「寸法」「のこと」，
就 100 分命中那个短词条。实测就这么错过：

| OCR 文本 | 命中的词条 | 改之前 | 改之后 |
| --- | --- | --- | --- |
| `の穴加工部は面取リのこと` | `のこと`(3字) | `（请）` | `孔加工部倒角` |
| `・カエリは完全に除去のニと` | `カエリ`(3字) | `飞边` | `⑧毛刺飞边完全去除。` |
| `5検穴加工部にシンブを圧入のこと` | `のこと`(3字) | `（请）` | `销孔加工部压入销` |
| `4Eł牝加工部の寸法形状はđ×ｆデ` | `寸法`(2字) | `尺寸` | `[未翻译]` |

所以候选词条先按长度过一遍：**只留长度至少占 OCR 文本 70% 的**。这条线是量出来的 ——
门槛放在 50% 时，整句 `2ランジクランプ穴はバリ取リのこ` 会命中只占半句的
`ランジクランプ穴`（它是子串，partial_ratio 照样给 100 分），译文只剩半截"法兰夹紧孔"；
收到 70% 之后整句词条才浮上来。实测 60%~80% 之间结果完全一样，取中间的 70%。

反过来不设限，词条比 OCR 文本长是正常的 —— 那是注記被切成两半的情况，正是部分匹配
要解决的。卡完之后上面几条要么给出正确译文，要么老老实实标成未匹配，不再硬凑一个短词。

代价是模糊匹配仍然会认错（阈值 85 是折中），所以 `match_method` 会写进结果里，
界面能筛出所有 `fuzzy` 的条目人工过一遍。

**同一行被切碎的框要接回整句。** OCR 检测的单位是"文本行"，但图纸上同一行常被空格、
表格线、引出线切成几段，检测器就吐几个框。每段单独查词典基本查不到 —— 实测
`②ランジクランプ穴はバリ取りのこと。` 被切成 `2ランジク` / `ランプ穴はバ` / `リ取リのこ`
三段，三段全都匹配失败（中间那段还被短词条吸成了"法兰"）。所以同一行的相邻框先按 x
接回一句再送翻译，样例的识别结果从 29 条降到 20 条，那句也恢复了完整译文。

间隙多大算"被切碎"是量出来的：同一句的碎片之间差 0.3 倍框高以内、甚至互相重叠，
而真正独立的两段标注最近也隔了 1.8 倍框高，门槛取中间的 1.0 倍。

代价是碎片里有一段 OCR 认得太烂时，接起来反而把原本能单独匹配的碎片一起拖下水 ——
样例里 `参照のこと` 单独能查到"请参照"，并进认花了的前半句之后变成未匹配了。

**所以接龙是可以退的：整句查不到就拆回碎片各自重查。** `_join()` 把每个碎片连同
它**自己的 bbox** 记进 `parts`，整句匹配失败时（`main_window._translate_item`）
逐片重查，然后把这一条拆回碎片、每片画回它原来的位置。样例里 `参照のこと` 因此
从"未翻译"回到"请参照"，而且画在自己的框上，不是整句的并集框。

只认**精确**命中才拆，模糊命中不算 —— 这条线是量出来的。模糊碎片会两头亏：整句那条
连同它自己的「疑似」一起消失（而整句的疑似往往更准，它更接近词典里的整句词条），
碎片自己还会掉进"长度门槛只挡一头"那个坑（见上面「已知局限」）。实测拆
`9公差はＪＩＳ / Ｂ0405 / 中級による` 那条：5 个字的 `中級による` 是整句词条的子串，
拿到 100 分，把整句译文贴进了自己的小框 —— 比不拆更糟。改成只认精确之后，这条保持
原样（未翻译 + 正确的疑似），而 `参照のこと` 那条照拆不误。

**间隙里有竖线就不接。** 光看间隙大小分不出"一句话被切开"和"表格的两栏挨得近"。
`_vertical_rule_mask()` 用形态学开运算抠出长竖线（结构元按字高的 2 倍定，不是按图高 ——
按图高在小图上会塌到比字还矮），间隙里横着一条竖线就否决合并。

关键是**只看竖线**：碎片是被"空格、表格线、**引出线**"切开的，而引出线多是斜的，
开运算之后剩不下几个像素。实测 demo 图上 `②ランジクランプ穴はバリ取りのこと。`
的四段碎片间隙竖线覆盖率都是 0%，接龙照常；而被否决的两处（`尺度|1:2`、
`…đ×ｆデ-`-|参照のこと`）经查都是标题栏里真实存在的格线。

这项只做否决、不促成合并，拿不准时退化成原行为。样例图上它能验证"不回归"，
验证不了"有收益"（最近的一对独立标注本来就隔了 1.82 倍框高，压根没被合并）——
`examples/test-rule.png` 是为这个造的判别图：同样的文字、字号、间隙，一组中间画竖线、
一组不画，只有前者不接。

**没有假名的行不翻。** 假名是"这行得翻"的信号：平假名扛语法（`のこと`、`取り`），
片假名是外来语（`カバー`、`アルマイト`），中文读者都读不出来。反过来，`技術部`、
`正面図`、`部品名`、`SUS304`、`縮尺1:2` 这种全汉字加数字符号的行，中文读者扫一眼就懂，
再拿红字盖一遍只是往图纸上添乱 —— 样例 20 条里 8 条属于这种，省掉之后图纸干净多了。

例外是"汉字陷阱"：`取代` 在中文里是"替换"，图纸上却是"加工余量"；`半田` 是"焊锡"，
不翻反而看不懂。这类词列在 `config.yaml` 的 `kanji_traps` 里，按自己的图纸慢慢补。

**不提供「盖住原文」模式。** 早期版本有个 `遮挡原文` 开关，勾上就用白底盖住日文、
译文画在原地。撤掉了 —— 因为**这是个核对工具**，把日文盖住等于把要核对的东西销毁，
用户没法再回头确认翻译对不对。`OverlayRenderer` 里那份实现没删，只是界面不再暴露它。

那份实现本身还有个代价，记在这里以防以后要重新开出来：白底铺的是「原文框 ∪ 译文
实际占位」的并集，不是只铺原文框。译文换行后可能比原文框高（标题栏那种窄格子尤其
明显），只盖原文框的话多出来的几行会直接压在没盖住的日文上。代价是白底偶尔会盖住
相邻的格子。

**两个置信度分开存。** OCR 的识别置信度和词典的匹配得分含义不同 —— 前者说「这行
日文认没认对」，后者说「这个词条找得准不准」。JSON 里分别是 `ocr_confidence` 和
`confidence`，表格里显示的是后者。合到一起就分不出某条未匹配到底是 OCR 认错了字，
还是词典里压根没这个词。

**差一点没够阈值的候选带回去当提示，但不当成翻译。** `partial_ratio` 算出的
`best, score` 在不够阈值时本来是要丢掉的，可"只差一点"恰恰是**认错一个字符**的
特征 —— 样例里 `カバー` 被认成 `力バ`（浊点丢了）、`面取り` 被认成 `面取リ`
（平假名り → 片假名リ），都落在差几分的位置上。现在这个候选会显示成
`[未翻译]（疑似 焊锡，67 分）`，鼠标悬停能看到完整词条。

提示线定在**阈值下 25 分**，是量出来的：真正的近似命中都落在 65~75 分；随机垃圾
（120 条随机字母数字 + 随机假名串）95 分位只有 40，120 条里只有 1 条够到 60 分以上。
两边在 60 分上下分开，没有干净的空档，但误报很便宜（只是让人多看一眼），漏报等于
把线索丢了，所以宁可把线放低。

必须说清楚的是：**这只是线索，不是答案** —— 分数高低区分不出候选对不对。样例里
`面取リ → C面取り`、`タツプ → タップ` 是对的，`力バ → 工程能力` 是错的，三个都是
67 分。它仍然是 `unmatched`，不参与「已翻译」的统计，界面上也是红色斜体 + `[未翻译]`
前缀。

**竖排/斜排标出来，但不接龙、不识别。** 排向在压成轴对齐矩形**之前**判（压完就
没信息了），用最小外接矩形和轴对齐矩形的**面积之比**：横平竖直时两者几乎相等，
斜着写时轴对齐矩形会胀大一圈。不碰 `cv2.minAreaRect` 的 angle —— 那个角度的正负号
和范围在 OpenCV 4.5 前后改过，照着写容易在换版本时悄悄判反，而且反了不报错。

竖排的框**不参与横向接龙**，因为接龙的尺度是框高：横排时框高约等于字号，正是它想当
的尺度；竖排时框高是**整列文字的长度**，半径被撑大几十倍。实测造的那张图上，一列
150px 高的竖排字把 100px 开外的一个横排接成了 `バリ取り面取り`。

**`use_angle_cls=False`。** PaddleOCR 的方向分类器是给自然场景照片（路牌、包装）
用的，机械图纸上的文字都是水平的，开了只会多一遍推理。要注意它**只管 0°/180°，
不管 90° 和任意角** —— 竖排/斜排指望它矫正是不行的，那段代码本来就没有方向路由。

**Windows OCR 作为回退。** PaddleOCR 装不上或模型下载失败时，退回系统自带的
Windows OCR（`winsdk`），保证软件还能用。它不提供逐行置信度，所以回退路径下所有
结果的 `ocr_confidence` 统一记 1.0 —— 那个 1.0 没有含义，只是占位。

## 实测：预处理参数对照实验

`preprocess()` 里有两个参数一直是拍脑袋定的，所以写了 `tools/exp_downsample.py`
做 2×2 对照，跑两张真实图纸：

- 大图 6350×4490（会触发下采样）
- 小图 2000×1400（两档 `max_dimension` 都不触发下采样，因此两组结果应当逐字一致，
  用来验证确实只动了 `deskew` 一个变量）

跑法：`python tools/exp_downsample.py`。机器是 Intel 12 代酷睿（16 线程）/
15.7 GB RAM / Windows 11 / Python 3.11.7。

**大图 6350×4490**

| max_dimension | deskew | 处理后尺寸 | 预处理 | OCR | 识别条数 |
| --- | --- | --- | --- | --- | --- |
| 3000 | 关 | 3000×2121 | 1.62s | 6.74s\* | 25 |
| 3000 | 开 | 3173×2374 | 3.25s | 1.40s | 16 |
| 不缩 | 关 | 6350×4490 | 7.06s | 1.17s | 21 |
| 不缩 | 开 | 6717×5026 | 12.62s | 0.85s | 17 |

\* 这是该次进程里的第一次 OCR，含模型加载，不能当作 OCR 耗时来比。

**小图 2000×1400（对照组）**

| max_dimension | deskew | 处理后尺寸 | 预处理 | OCR | 识别条数 |
| --- | --- | --- | --- | --- | --- |
| 3000 | 关 | 2000×1400 | 0.64s | 1.20s | 29 |
| 3000 | 开 | 2135×1601 | 1.19s | 1.12s | 27 |
| 不缩 | 关 | 2000×1400 | 0.61s | 0.93s | 29 |
| 不缩 | 开 | 2135×1601 | 1.15s | 0.77s | 27 |

小图里 `max_dimension` 两档结果逐字一致（`deskew` 关时 29 条对 29 条，开时 27 条
对 27 条），说明对照成立，下面看到的差异确实来自 `deskew`。

**结论一：倾斜校正要关，`config.yaml` 里 `deskew: false` 是对的。**

四种组合里，开了旋转的一致更差：大图 25→16、21→17，小图 29→27。逐词看更明显：
`参照のこと` 在小图上开旋转后直接识别不到；`カエリは完全に除去のこと` 被切成
`カエリは完全に除去のこ`，把数字 `0` 认成了 `ニ`。

原因在 `_detect_skew_angle()`：它用霍夫变换求所有直线倾角的中位数，但机械图纸横线、
竖线、斜线都有，这个「中位数」没有意义。实测中一张完全水平的图纸被判成 -6°
（整数是因为 `HoughLines` 的角度分辨率就是 1°），转完之后 OCR 反而变差。

**结论二：下采样到 3000 的收益说不清楚，所以关了。**

大图上 3000 这一档多识别出 4 条，但那 4 条是 `DO.Oo0- f.Du?`、`I'l?.` 这类噪声，
不是真词；而 `ダイセット` 在不缩的那两档反而更完整。代价是预处理从 1.6s 涨到 7.1s
（不缩 + 旋转时 12.6s）。所以 `config.yaml` 里 `max_dimension` 留 `null`。

**这个实验有个反例，也记在这里。** 实验开始前预期被切碎的 `硬度HRC` 会在
「不缩 / 不转」那一档恢复，实际它只在「不缩 / 转」这一档出现，9 个追踪词里就这
一个是这样。单点差异，不足以下相反的结论，但也不该当作没看见。

## 词典自检

```
python tools/check_dictionary.py [词典路径]
```

词条写错了不会报错，只会安静地输出一条读不通的译文 —— 这是最难发现的一类问题，
因为界面上它和"翻对了"长得一模一样。这个脚本把能在**跑之前**查出来的几类挑出来，
有问题时退出码为 1，可以直接挂到 CI 上。

它复用 `Translator.load_dictionary()` 读词典，不自己 `json.load` —— 加载时会按
`translator.py` 的规则过滤掉空值和 `___`/`===`/`//`/`#` 开头的注释键，自己读会
把那 22 个注释键也当成词条扫进来，报一堆假问题。

963 条上的实测结果：

| 检查 | 结果 |
| --- | --- |
| 1. 中文值里含假名 | 无 —— 没有"抄了一半"的词条 |
| 2. 键互为子串而译文不同 | **61 对**长度比过线，运行时的 70% 门槛挡不住 |
| 3. 译文与原词相同 | **142 条**，全是 `CAD → CAD`、`HRC → HRC` 这种。多半是有意留的（希望它们显示成"已翻译"而不是"未匹配"），但**同样因为没假名，跳过规则在查词典之前就 return 了**，实际一条都不生效 |
| 4. 多个键译成同一个中文 | **94 组**，多数是同词的长短写法（`焼入`/`焼入れ` 都译「淬火」），不算错 |
| 5. 空值 / 被静默丢掉的条目 | 无（985 原始键 = 963 有效 + 22 注释） |
| 6. 键只差结尾标点或全半角 | **13 组** |
| 7. 无假名的键（永远走不到精确匹配） | **453 条**（占 47%），其中**字母/缩写类 26 条** |

第 3 条和第 7 条说的是同一批条目的两个侧面：它们既"译了等于没译"，又"根本走不到"。
留着不算错，但 `CAD` 这种如果本意是想让它出现在结果里，得先改跳过规则 —— 光写进
词典是没用的。

第 2 条最值得看。`めねじ`⊂`止めねじ`、`ザグリ`⊂`平ザグリ`/`皿ザグリ`/`逆ザグリ`、
`面取り`⊂`C面取り`/`R面取り`、`許容差`⊂`上許容差`/`下許容差` —— 被丢掉的限定词
（非/半/中/上/下/C/R/皿/平/逆）**恰恰是决定意思的那个**。脚本按运行时的门槛把
"危险"和"已被挡住"分开报，不一股脑列出来。

第 6 条在样例里就能看见后果：词典里同时有 `EWC加工部の寸法形状はdxfデータ参照のこと`
和它的带句号版本，模糊匹配要在两条只差一个 `。` 的候选之间挑，挑哪条是随机的。

第 7 条是「纯汉字就不翻」这条规则真正的漏洞。规则的判据是"有没有假名"，它想表达的
却是"中文读者看不看得懂"，两者**在字母缩写上正好错开** —— `NG`→不合格、`OK`→合格、
`MOQ`→最小起订量、`NC旋盤`→数控车床、`WED`→线切割、`REV`→版本。这些没有假名，
中文读者也读不出来，却被同一条规则一起跳过，词典里给它们写的译文一辈子不出现。
脚本把「字母/缩写类」和「汉字类」分开报：前者是漏洞，后者（`技術部`、`正面図`）
跳过是对的，只报个数。

这些都是**疑似**，不是错误 —— 子串对在术语词典里很常见且合理（`座金`/`座金具`
都译「垫圈」就不冲突，第 2 条不会报）。脚本只列清单，不做修改，要不要动由人判断。

## 已知局限

- **词典覆盖有限。** 963 条覆盖不了图纸上所有写法，没命中的原文会原样标成
  `[未翻译]` 保留在图上，不会瞎猜。样例里 21 条有 3 条是这种情况（这 3 条会带
  「疑似」提示，见下）
- **条目数会随合并/拆分变化。** OCR 把被切开的句子接成整句、或整句查不到时又
  拆回碎片，都会让条目数变。样例的 21 条不是"图纸上有 21 处文字"，是"这一版
  分成了 21 条"。要稳定的口径请看 JSON 里的坐标，不要看条数
- **模糊匹配会认错。** 阈值默认 85，调低能多认几个词，也更容易认错。结果里的
  `match_method` 就是为了筛出这些 —— 复核时只看 `fuzzy` 那些即可
- **"疑似"只是线索，不是答案。** 差一点没够阈值的候选会显示成
  `[未翻译]（疑似 X，N 分）`。分数高低**区分不出候选对不对**：样例里
  `面取リ → C面取り`、`タツプ → タップ` 是对的，`力バ → 工程能力` 是错的，
  三个都是 67 分。它仍然是 `unmatched`，不参与「已翻译」的统计
- **"不需要翻译"是估出来的。** 判定只看有没有假名，所以纯汉字的生僻写法
  （`半田`、`取代` 这类）要靠 `kanji_traps` 名单兜，名单之外的会漏。
  字母缩写类另外是个漏洞 —— `NG`、`MOQ`、`NC旋盤` 没有假名，中文读者也读不出来，
  却被同一条规则一起跳过了。`tools/check_dictionary.py` 会把这类列出来
- **同行合并可能并错。** 间隙门槛是 1.0 倍框高。间隙里有竖线时会被否决（表格的
  两栏不该接），但**检测器把表格线本身读成文本块时拦不住** —— 那时线在一个框里，
  不在间隙里
- **模糊匹配的长度门槛只挡一头。** 它要求候选词条不能比 OCR 文本短太多
  （≥ 70%），但**不限制候选比文本长多少**。而 `partial_ratio` 在"短串是长串
  子串"时恒给 100 分，于是一个 5 个字的碎片只要是某个整句词条的子串，就会拿到
  100 分、把整句的译文贴进自己的小框里。实测：`中級による` → `⑨公差按JIS B 0405
  中级。`（100 分）。这是编号错位，不是翻译错误，但看上去很像"翻对了"
- **OCR 本身会认错字。** 样例里 `カバー` 被认成 `力バ`（浊点丢了），
  `面取り` 被认成 `面取リ`（平假名り → 片假名リ）。这类错误词典救不了，
  只能靠提高分辨率或人工核对
- **竖排/斜排只标出来，不支持。** 检测到排向会在结果表里标成「竖」「斜」
  （全横排时这一列自动隐藏），并且**不参与横向接龙** —— 竖排的框高是整列字的
  长度，用它当合并半径会大得能横跨半张图纸。但识别本身没做方向路由：竖排多半
  认不出或认错，倾斜超过约 4° 的文字检测器可能直接不给框。`use_angle_cls=False`
- **倾斜校正默认关闭**，原因见上面的实测；真要开，`config.yaml` 里改成 `true`
- **Windows OCR 回退路径没有置信度**，统一记 1.0，`min_confidence` 对它不起作用；
  也没有多边形，判不出排向，一律按横排
- **不支持拖放打开文件**，只能用菜单或工具栏
- **多页时 ID 会在每页内重新编号**，跨页重号。图上的高亮不受影响（只画当前页），
  但"点表格跳图"在跨页时会命中前一页的同号条目
- **只在 Windows 上验证过**

## 依赖

PaddleOCR（OCR 引擎）、PyQt5（界面）、OpenCV + Pillow（图像处理）、FuzzyWuzzy +
python-Levenshtein（模糊匹配）、pdf2image + pypdf（PDF 解析）、PyYAML（配置）。
完整清单和版本要求见 `requirements.txt`。

`winsdk` 是可选的：只在 PaddleOCR 不可用时作为回退路径被加载，装不上不影响主流程。
